# brainstorm: 工作项积分审核模块

## Goal

新增一个“工作项积分”大模块，支持管理员维护可申报的工作项类型与评分规则，员工按日选择并提交自己完成的工作项及图片佐证，管理员按评分标准审核、打分、退回修改或通过锁定，最终形成指定时间段内所有人员总分报表。

## What I already know

* 用户期望页面左右分布：按类型组织工作项，每个类型下维护多个工作项。
* 管理员维护内容大致包括：类型、工作项、描述、评分标准、分数等。
* 普通用户每天按实际情况维护自己完成的工作项，需要操作便捷，支持上传图片佐证，维护好后提交。
* 管理员负责审核，根据标准分打分。
* 审核不通过时退回给提交人修改。
* 审核通过后，当天分数确定，不再允许提交人修改。
* 需要总报表，可查询所有人在指定时间段的总分。
* 当前任务目录为 `.trellis/tasks/05-28-work-item-score-review`，任务状态为 `planning`。
* 当前仓库主后端为 `smart-admin-api-java8-springboot2`，业务模块通常放在 `sa-admin/src/main/java/net/lab1024/sa/admin/module/business/**`。
* 当前仓库主前端为 `smart-admin-web-typescript`，后台页面通常放在 `src/views/business/**`，接口封装放在 `src/api/business/**`。
* 仓库中暂未发现已有 `工作项` 或 `积分审核` 业务模块，需要按新业务模块处理。
* 项目已有文件上传能力：
  * 前端 API：`smart-admin-web-typescript/src/api/support/file-api.ts`
  * 前端组件：`smart-admin-web-typescript/src/components/support/file-upload/index.vue`
  * 后端接口：`/support/file/upload`
  * 后端上传服务：`FileService` / `IFileStorageService`
  * 上传成功后可获得 `fileId`、`fileName`、`fileUrl`、`fileKey` 等信息。
* 项目菜单与权限是动态菜单体系：登录后按 `t_menu.component` 动态加载 `views/**.vue`，新增页面应配套菜单和权限初始化 SQL。
* 当前工作树已有 4 个 `sa-base.yaml` 未提交配置改动，本任务不触碰。

## Assumptions (temporary)

* 该模块属于业务模块，优先放在 `sa-admin` 的 `module/business` 下，而不是 `sa-base` 支撑模块。
* 前端优先只实现后台管理端 `smart-admin-web-typescript`，暂不实现移动端 `smart-app`。
* “当天分打出来了，不再允许修改”理解为：整张日报审核通过后，当天日报和明细全部锁定；审核失败退回后允许提交人修改后再次提交。
* 管理员审核时按明细逐项打分，但最终审核结果是整张日报通过或失败。

## Decisions

* 本期包含补填/逾期填报规则，补填期限复用现有系统参数配置页面维护。
* 本期不做批量审核。
* 日报明细保存工作项名称、类型、标准分等快照，历史已通过日报不受后续工作项规则修改影响。
* 新模块新增 4 个页面：工作项维护、我的日报、日报审核、积分报表；不新增模块设置页。
* 核心流程已确认：管理员维护规则和参数；员工按日期维护日报草稿并提交；管理员按明细打分并整张通过或失败；失败后员工可编辑整张日报重新提交；通过后日报锁定并进入报表统计。
* 数据模型采用“日报主表 + 明细表 + 明细附件表 + 审核历史表”方案，并单独维护工作项类型表、工作项表。
* 草稿和审核失败后的日报重新提交时，日报明细快照刷新为最新工作项名称、类型、标准分、评分标准；审核通过后的日报保持历史快照不变。
* 系统保留每次审核历史；日报主表保存当前最新状态，审核历史记录审核人、审核时间、审核结果、失败原因等。

## Decision (ADR-lite)

**Context**: 业务规则要求员工每天一张日报、日报内多条明细、每条明细可上传图片、管理员按明细打分但整张日报统一通过或失败，报表需要从人员总分下钻到日期、类型、工作项。

**Decision**: 采用独立类型表、工作项表、日报主表、日报明细表、明细附件表、审核历史表：

* `work_item_type`：工作项类型。
* `work_item`：可申报工作项及评分标准。
* `work_daily_report`：日报主表，记录员工、日期、状态、审核结果。
* `work_daily_report_item`：日报明细，记录工作项快照、说明、标准分、最终分、扣分原因。
* `work_daily_report_file`：日报明细图片，关联明细和上传文件。
* `work_daily_report_audit`：审核历史，记录每次审核动作、审核人、审核时间、审核结果和失败原因。

**Consequences**: 数据边界清晰，适合整张审核、明细打分、图片佐证和报表下钻；表数量略多，但能避免逗号字段或 JSON 附件导致的查询和维护困难。

## Data Snapshot Rules

* 草稿保存阶段可以记录当前选择的工作项和临时展示分数。
* 提交审核时，以当前工作项配置刷新日报明细快照，包括工作项名称、类型名称、标准分、评分标准等。
* 审核失败后员工重新提交时，再次按最新工作项配置刷新未通过日报的明细快照。
* 审核通过后，日报和明细锁定，历史快照不再随工作项配置变化。

## Audit History Rules

* 每次管理员审核日报时，都新增一条审核历史。
* 审核历史至少记录日报 ID、审核结果、失败原因、审核人、审核时间。
* 日报主表保存当前最新状态、最新审核人、最新审核时间、最新失败原因，便于列表查询。
* 审核历史用于详情页追溯，不替代日报主表的当前状态字段。

## Status And Scoring Rules

* 日报状态包括：草稿、待审核、审核通过、审核失败。
* 状态流转为：草稿 -> 待审核；待审核 -> 审核通过；待审核 -> 审核失败；审核失败 -> 待审核。
* 草稿状态下，提交人可编辑整张日报。
* 待审核状态下，提交人不可编辑，管理员可审核。
* 审核失败状态下，提交人可编辑整张日报并重新提交。
* 审核通过状态下，提交人不可编辑，管理员不再重复审核。
* 明细最终分默认等于标准分，管理员审核时可修改最终分。
* 明细扣分原因可选，不强制填写。
* 整张日报审核通过后，报表按明细最终分合计计分。
* 整张日报审核失败时不计入报表。

## Page Design

### 工作项维护

* 左侧展示工作项类型，支持新增、编辑、停用、排序。
* 右侧展示当前类型下的工作项列表，支持搜索、新增、编辑、停用、排序。
* 工作项字段包括名称、描述、评分标准、标准分、启用状态、排序。

### 我的日报

* 顶部展示日期、日报状态、允许补填提示，并提供保存草稿、提交审核操作。
* 左侧展示工作项类型。
* 中间展示可选工作项列表，支持搜索；已添加项显示“已添加”，不可重复添加。
* 右侧展示已填明细，按类型分组；每条明细支持编辑完成说明、上传图片、删除。
* 草稿和审核失败状态可编辑；待审核和审核通过状态只读。

### 日报审核

* 列表支持按日期、员工、状态查询日报。
* 详情展示员工、日期、明细、图片、历史审核记录。
* 审核时每条明细默认标准分，可修改最终分，可选填写扣分原因。
* 整张日报执行通过或失败；失败必须填写具体原因。

### 积分报表

* 查询条件包括起止日期、员工、部门。
* 主表展示人员总分、通过日报天数、明细数量。
* 支持从人员下钻到日期、工作项类型、工作项明细。

## Permission And Validation Rules

### 普通员工

* 可查看自己的日报。
* 可新建、编辑自己的草稿日报和审核失败日报。
* 可保存草稿。
* 可提交审核。
* 可查看自己的审核结果、失败原因和明细扣分原因。
* 可查看自己日报明细关联的图片。

### 管理员

* 可维护工作项类型。
* 可维护工作项。
* 可查看所有人的日报。
* 可审核日报。
* 可查看积分报表。
* 可通过现有参数配置页面维护允许补填天数。

### 后端强校验

* 员工只能修改自己的日报。
* 只有草稿和审核失败状态可编辑。
* 只有待审核状态可审核。
* 审核通过后禁止修改和重复审核。
* 超出允许补填天数禁止新建或提交日报。
* 同一张日报内不能重复添加同一工作项。

## Requirements (evolving)

* 管理员可以维护工作项类型。
* 管理员可以在类型下维护多个工作项。
* 工作项至少包含名称、描述、评分标准、标准分、启用状态、排序。
* 管理员可以在现有参数配置页面维护“允许补填天数”，页面路径为 `/#/config/config-list`，默认值为 2 天。
* 工作项维护页面采用左侧类型、右侧工作项列表/表单的布局。
* 我的日报页面用于员工按日期填写、上传佐证、提交审核；采用三栏结构：左侧工作项类型，中间可选工作项列表，右侧已填明细。
* 我的日报中间可选工作项列表支持搜索；已添加的工作项显示“已添加”状态，不允许重复添加，点击可定位到右侧已填明细。
* 我的日报右侧已填明细作为主操作区，按类型分组展示；每条明细显示工作项名称、标准分、完成说明、图片数量，并支持编辑、删除。
* 我的日报支持手动保存草稿；草稿状态可编辑，提交后进入待审核。
* 日报审核页面用于管理员查看待审核日报、逐明细打分、整张通过或失败。
* 积分报表页面用于按时间段查询人员总分，并下钻到日期、类型、工作项明细。
* MVP 范围一次包含完整闭环：规则维护、每日申报、图片佐证、审核打分、通过锁定、退回修改、汇总报表。
* 普通用户按“每天一张日报单”维护完成情况：单据头记录员工和日期，单据明细包含多个完成工作项。
* 普通用户创建或提交日报时，需要校验填报日期是否在“允许补填天数”范围内；默认允许补填 2 天。
* 同一员工同一天同一工作项不允许重复申报；一张日报单内同一工作项只能出现一次。
* 普通用户在每条日报明细上上传一张或多张图片作为佐证，图片与具体工作项明细绑定。
* 普通用户完成维护后提交审核。
* 管理员可以查看草稿、待审核、审核通过、审核失败等日报。
* 审核采用“整张日报统一状态 + 明细逐项打分”模式：管理员在一张日报内对每条明细填写最终分。
* 明细最终分默认带出工作项标准分，管理员可手动调整。
* 明细存在扣分时，可选填写该项扣分原因；系统不强制。
* 整张日报审核失败时，管理员必须填写具体失败原因，提交人可修改后再次提交。
* 整张日报审核失败退回后，提交人可以编辑整张日报，包括修改说明、调整图片、新增明细、删除明细，然后重新提交。
* 整张日报审核通过后，当天日报锁定，提交人不允许再修改或删除，报表按明细最终分合计计分。
* 审核通过后不生成独立积分流水，报表直接统计审核通过日报的明细最终分。
* 报表支持按时间段查询所有人员总分，并可下钻查看日期明细、工作项类型明细、工作项明细。
